# CardBreakPro — Functional Correctness & Scale-Readiness Audit

**Date:** 2026-09-18 · **Scope:** logic correctness, scale readiness (5–10× current volume), code quality. Security and data-privacy are explicitly out of scope (separate pass).
**Method:** static read of every core module in priority order, tracing the math paths end to end. No live DB access — where a finding depends on a production setting I could not read (PostgREST max-rows, columns that live only in prod), it is marked *inferred* and comes with a one-line verification query.
**Severity:** **CRITICAL** = money is wrong today · **HIGH** = wrong data or broken feature in normal use · **MEDIUM** = wrong under common edge cases / will break at scale · **LOW** = cosmetic, latent, or debt.

---

## 1. Architecture in one paragraph

Four static HTML apps (`owner.html` 11.5k lines, `breaker.html` 4.4k, `manager.html` 3.6k, `sorter.html` 2.1k) talk to Supabase directly with the anon key + RLS for ~90% of reads/writes, and to a handful of Vercel serverless functions for anything needing the service role or Stripe: `api/features.js` (a 1,500-line router for chat, leaderboard, milestones, sorter splits, goals, notifications, analytics, stream delete, team remove — one file because of the Vercel Hobby 12-function cap), `api/cron.js` (7 daily jobs via `vercel.json` crons), `api/process-import.js` / `import-slip.js` (packing-slip → buyers), `stripe-webhook.js` + billing helpers. Core flow: breaker enters a **stream key** → each break is inserted into `breaks` and its products are decremented in `products` (client-side read-modify-write) → `streams.total_*` are running denormalized sums → at closeout the breaker imports the Whatnot slip (`buyer_purchases` are the source of truth; `buyers.total_*` are recomputed server-side), enters `final_sales`, and the stream is closed with a snapshot `commission_payout`; closing creates a `sort_tasks` row, notifies sorters, and updates `leaderboard_snapshots` / `monthly_goals`. Owner payroll, dashboards, ROI, performance, and history are all computed **in the browser** from full-table pulls of `breaks` / `streams` / `schedules`; only the buyer CRM (`buyer-intel.js`, rebuilt this week) uses server-side rollups and paging. Schema in the repo is partial: `schedules`, `channels`, `channel_assignments`, `tips`, `sort_tasks`, `payroll_runs`, `inventory_log`, `activity_log` have no DDL here (see CQ-3).

## 5. Verdict
